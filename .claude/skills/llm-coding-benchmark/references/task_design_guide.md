# タスク設計ガイド

## 複雑さの段階分け(推奨: 3段階)

モデル間の差は「シンプルなタスクでは出ない/複雑なタスクで広がる」という傾向が出やすい。段階を分けることで、仮説を「どのレベルの複雑さまでなら代替可能か」という形で検証できる。

Terraform/AWSの例:

| 段階 | 内容例 |
| --- | --- |
| シンプル | 単一リソース(S3バケット単体等)。設定項目は数個 |
| 中程度 | 複数リソースが連携する基本構成(VPC+EC2+SG等) |
| 複雑 | 複数レイヤーが連携し、非機能要件(セキュリティ・可用性)が絡む構成(ALB+ASG+RDS+IAM等) |

他ドメインでも同じ考え方を使う。例えばPythonスクリプトなら「単一関数」「複数モジュール連携」「エラーハンドリング・リトライを含む本番相当の処理」のような3段階。

## プロンプトの書き方

- 要件は番号付き・箇条書きで列挙し、解釈の余地を減らす
- 出力形式を固定する一文を必ず入れる(例: 「説明文は不要です。コードのみを出力してください」)
- 複数ファイルに分けることを許可する場合、分割時のマーカー規約を明示する(後続のパース処理と対応させる)
- タスク自体にコーディング規約や非機能要件を混ぜない(それ自体を検証したい場合は、規約なし版とは別ファイルで管理する。本スキルのステップ7を参照)

## タスクファイルの保存

- `tasks/<task_name>.md` として平文で保存する
- ファイル名はスラッグ化した短い名前にする(例: `task1_simple.md`)。後の生成・評価スクリプトでディレクトリ名としてそのまま使うため
