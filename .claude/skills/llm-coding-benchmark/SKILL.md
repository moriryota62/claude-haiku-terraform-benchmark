# LLM コーディング品質ベンチマーク → Qiita記事化

ユーザーの仮説(例:「軽量モデルでも重量モデルの代替になるのでは」)を、複数モデルに同一タスクを与えて客観的指標で採点するベンチマークに落とし込み、検証結果をQiita記事の下書きに仕上げる一連の流れを行う。

このスキルは「人間の主観によるレビューではなく、機械的に判定できる指標で比較する」ことを徹底する。コード品質の良し悪しを言葉で評価するのではなく、`terraform validate`やlinter、静的解析ツールなど、再現可能な指標でスコア化する。

## 全体の流れ

1. 仮説と検証スコープのヒアリング
2. タスク設計(複雑さの異なる複数タスク)
3. 評価指標の設計(機械的に判定可能な指標のみ)
4. モデル呼び出しスクリプトの作成・実行
5. 評価スクリプトの作成・実行
6. 結果レポートの生成
7. (任意)追加検証: 明示的な指示の有無での比較
8. ユーザーの過去記事を参照したQiita記事の執筆
9. (任意)GitHubリポジトリとしての公開

各ステップは順番に進めるが、ステップ1・2・8は必ずユーザーとすり合わせる。それ以外は自律的に進めてよい。

---

## ステップ1: 仮説と検証スコープのヒアリング

ユーザーの発言から以下を特定する。特定できない項目があれば、仮の方針を立てずに `AskUserQuestion` で確認する。

- **仮説**: 何を確かめたいか(例: 「Haiku 5.5はSonnet 5.5のTerraformコーディング代替になるか」)
- **比較対象のモデル**: 何個のモデルを比較するか、モデルIDは何か
  - AWS Bedrockの場合、`mcp__awslabs-aws-knowledge-mcp-server__aws___search_documentation` でモデルカードを検索し、正確な推論プロファイルID(`us.anthropic.claude-xxx`等)を確認する。記憶で書かない
  - API直叩きの場合はAPIキーの有無を確認する
- **タスクの対象領域**: 言語・ドメイン(Terraform/AWS、Pythonスクリプト、SQL等)
- **タスクの規模感**: 何段階の複雑さを用意するか(推奨: 3段階。シンプル/中程度/複雑)

これらが決まったら、次のステップに進む前に簡潔に要約し、認識を合わせる。

---

## ステップ2: タスク設計

[references/task_design_guide.md](references/task_design_guide.md) の指針に従い、複雑さの異なる複数タスクを設計する。各タスクは以下の条件を満たすこと。

- 要件が一意に解釈でき、モデルによって「要件の解釈」自体が割れないこと
- 「説明文は不要、コードのみ出力」のように、出力形式を揃える指示を含めること
- 複数ファイルに分割する場合の規約(例: `# ファイル名: xxx.tf` のマーカー)を指示に含め、後続のパース処理と整合させること

タスク定義は `tasks/*.md` のような平文ファイルとして保存し、プロンプトそのものをファイルに残す(後からモデルに何を指示したか追跡できるようにする)。

---

## ステップ3: 評価指標の設計

機械的に判定可能な指標のみを採用する。候補は [references/evaluation_axes.md](references/evaluation_axes.md) を参照。最低限、以下の軸をカバーすることを推奨する。

- **構文・実行可能性**: 対象言語のバリデータ(`terraform validate`、`python -m py_compile`等)
- **静的解析・ベストプラクティス**: 対象言語のlinter(tflint、ESLint、pylint等)
- **セキュリティ**: 可能であればセキュリティスキャナ(checkov、tfsec、bandit等)
- **要件カバレッジ**: タスクで指定した必須要素が実装されているか(正規表現または構造解析で検出)
- **コーディング規約準拠**: 命名規則・ドキュメンテーション記載など、ユーザーが明示していない場合でもモデルが自発的に守るかを見る指標
- **アンチパターン検出**: セキュリティ上の明らかな問題(認証情報のハードコード、過度に広いアクセス許可等)

**正規表現で複合条件をチェックする際の注意**: 「Aという文字列とBという文字列がファイル中に存在する」という判定は、AとBが別々の箇所にあっても真になってしまう誤検知を生む(例: 「22番ポート」の存在と「0.0.0.0/0」の存在を別々に見ると、全く別のルールの組み合わせを拾ってしまう)。ブロック単位・リソース単位で範囲を絞ってから判定すること。

ツールのインストールが必要な場合は、先にBashで `which <tool>` を確認し、無ければ `brew install` やGitHub Releaseから導入する。brewにformulaが無いツール(tflint等)はGitHub Releaseのバイナリを `~/.local/bin` 等のユーザー権限で書けるディレクトリに配置する(sudoを避ける)。

## ステップ4: モデル呼び出しスクリプトの作成・実行

[references/generate_template.py](references/generate_template.py) をベースに、対象のタスク一覧・モデル一覧に合わせたコード生成スクリプトを作成する。

ポイント:

- モデルへの指示(プロンプト)は`tasks/`配下のファイルをそのまま読み込む。スクリプト内にプロンプトをハードコードしない
- レスポンス全文を`_raw_response.md`として保存する(後から抽出ロジックの不備に気づいた際に再パースできるようにするため)
- 複数ファイル出力のパース処理は、単一コードブロック内にファイルマーカーが埋め込まれるケース(モデルが指示を守らずコードブロックを1つにまとめる場合)も想定して書く
- 推論パラメータ(temperature等)はモデルによって非対応のことがある(Claude 5系はtemperature未対応等)。エラーが出たら素直にパラメータを削る

実行は `--models`・`--tasks` のようなCLI引数で部分実行できるようにし、まず1モデル×1タスクで小さく動作確認してから全体を流す。

---

## ステップ5: 評価スクリプトの作成・実行

[references/evaluate_template.py](references/evaluate_template.py) をベースに、ステップ3で設計した指標を実装する。

- 各ツールの出力は`--output json`等でJSON取得し、構造化データとして`results/raw_results.json`に保存する
- 1モデル×1タスクで動作確認してから全パターンに展開する
- セキュリティアンチパターンのような自作ロジックは、実際に生成されたコードを手動で2〜3件確認し、誤検知がないか検証する。誤検知が疑われたら実際のコード(`generated/*/*/*.tf`等)を`grep`等で直接確認して裏取りする

---

## ステップ6: 結果レポートの生成

[references/report_template.py](references/report_template.py) をベースに、`results/raw_results.json` から人間が読めるMarkdownレポートを生成する。

- スコアの重み付けは、各指標の重要度に応じて合計100点になるよう配分する
- タスクごとの総合スコア表、詳細結果テーブル、スコア算出方法の説明を含める
- 数値だけでなく、「どのチェックで何が引かれたか」の内訳(違反リスト等)も残す。記事を書く際に「なぜその点数になったか」を具体例で語れるようにするため

---

## ステップ7(任意): 明示的な指示の有無での比較

ベンチマークの結果、「全モデルで差がつかなかった」指標がある場合、それが「指示すれば誰でも守れるから差がつかない」のか「指示しても差がつく(モデルの能力差)」のかを追加で検証する価値がある。

手順:

1. 元のタスクプロンプトの末尾に、検証したい規約・要件を明示的に追記したバリアント(例: `task1_simple_conv.md`)を作る
2. 同じモデル・同じ生成/評価スクリプトでバリアント版を実行する
3. 「指示なし」と「指示あり」の準拠率を比較する

この比較は「モデル選定」と「プロンプト設計」のどちらが品質に効くか、という実務的に価値の高い示唆を生む。記事に加える場合は独立したセクションとして扱う。

## ステップ8: Qiita記事の執筆

### 8-1. ユーザーの文体を学習する

記事を書く前に、必ずユーザーの過去記事を参照して文体を揃える。

```bash
curl -s "https://qiita.com/api/v2/users/<ユーザー名>/items?per_page=20"
```

で記事一覧を取得し、検証系・技術ガイド系の記事を2〜3本選んで本文を取得する。

```bash
curl -s "https://qiita.com/api/v2/items/<item_id>"
```

学習すべき観点:

- 見出し構成の型(「はじめに」→「検証方針」→「検証」(検証/結果/気づき の繰り返し)→「まとめ」等)
- 一人称の推量表現の強さ(「〜と考えました」「〜でしょうか」等、断定を避ける度合い)
- 強調(太字)の使用頻度・絵文字の有無
- 結論を先出しするか、積み上げて最後に出すか
- セクション見出しの命名(「考察」のような硬い言葉を避けているか等、過去にユーザーから指摘された言い回しがあれば踏襲する)

### 8-2. 記事を書く

以下の型を基本とする(過去記事で確認された型。ユーザーの文体学習結果で上書きしてよい):

1. **はじめに**: 仮説・モチベーション → 検証した結果の要約(結論を先出し)
2. **検証方針**: 何を確かめたいか、どう確かめるか(タスク設計・評価方法)
3. **検証**: 指標ごとに「結果の表」→「見えてきたこと(気づき)」を繰り返す
4. **まとめ**: 観点ごとの結果を表で整理 → 仮説への回答 → 実務への示唆

執筆時の注意:

- 数値は`results/report.md`から正確に転記する。記憶や概算で書かない
- 「3モデルとも差がなかった」と「3モデルとも実装はできたが明示的な指示なしでは一部守れなかった」のような、結果の粒度を混同しない。何を検証した結果の数値かを明示する
- GitHubリポジトリで公開する場合、記事末尾にリンクを置く。リポジトリ名はタスク内容が外部から推測できる名前にする(過去の作業ディレクトリ名をそのまま使わない)

### 8-3. ユーザーに確認する

記事の下書きができたら、そのまま投稿せず、ユーザーに下書きとして提示する。Qiitaへの実際の投稿(公開操作)はユーザーの明示的な指示があるまで行わない。

## ステップ9(任意): GitHubリポジトリとしての公開

ユーザーがコードの公開を求めた場合のみ実施する。

- リポジトリ名は内容を反映した名前を提案する(候補を2〜4個出し、`AskUserQuestion`で選んでもらう)
- 既存のリモート設定(`git remote -v`)を確認し、無関係な既存リポジトリを指していないか確認する。重複や空リポジトリが見つかった場合はユーザーに扱いを確認する(削除権限が無い場合は手動削除を依頼する)
- push前に機密情報(アカウントID、認証情報等)が含まれていないか`grep`で確認する
- `.gitignore`で`.terraform/`、`*.tfstate`等の実行時生成物を除外する
- Qiita記事ファイル(`qiita_article.md`等)をリポジトリに含めるかどうかはユーザーに確認する。含めない場合は`.gitignore`に追加し、`git rm --cached`で追跡を外す(ファイル自体はローカルに残す)

---

## 進め方の原則

- **ユーザーに確認すべきこと**: 仮説のスコープ、モデル・タスクの規模、記事の公開可否、リポジトリ名、破壊的なgit操作
- **自律的に進めてよいこと**: ツールのインストール、生成・評価スクリプトの実装、動作確認、レポート生成
- **検証の信頼性を守るための習慣**: 評価ロジックに疑わしい結果が出たら(全モデルで同じ違反が出る、極端なスコア差が出る等)、実際の生成コードを目視で確認してロジックの誤りを疑う。ロジックのバグを疑わずに結果をそのまま記事化しない
